# Бриф фронтенд-агенту: экран настроек прогноза (forecast profiles)

Задача: экран, на котором человек смотрит и меняет параметры модели прогноза ACYS.

Документ состоит из трёх частей: **контракт API** (что читать и куда писать), **параметры** (техническое и
простое описание каждого — тексты можно брать в интерфейс как есть) и **требования к UI** (места, где легко
сделать неправильно).

---

## 1. Контракт API

Все ручки живут под `/forecast`, требуют авторизации (`X-Api-Key` со скоупом `predictive:read` для чтения и
`predictive:write` для записи, либо мастер-токен `X-Service-Token`) и возвращают общий конверт:

```json
{
  "status_code": 200,
  "details": { "msg": "Success", "correlationId": "8f4d3bf2-..." },
  "data": { }
}
```

Полезная нагрузка всегда в `data`. При ошибке `details.msg` — текст, который можно показать пользователю;
`correlationId` стоит логировать, по нему ищется серверная сторона проблемы.

### 1.1. `GET /forecast/params/schema` — описание формы

**Форму рисовать из этого ответа, а не из хардкода.** Добавление новой ручки в модель не должно требовать
релиза фронтенда.

```json
{
  "model_version": "acys-v1",
  "groups": ["History", "Level (volume)", "Seasonality", "Data frontier", "Route structure", "Horizon"],
  "params": [
    {
      "name": "level_window",
      "type": "int",
      "default": 15,
      "min": 3,
      "max": 36,
      "group": "Level (volume)",
      "label": "Level window, months",
      "description": "How many recent months are considered ..."
    }
  ]
}
```

Особенности, которые нужно учесть:

* `groups` — порядок секций формы. Группировать поля по `param.group`, секции выводить в порядке `groups`.
* `min` / `max` **могут отсутствовать** (у `history_start` их нет). Не полагаться на `null` — проверять
  наличие ключа.
* `type` — один из `int` | `float` | `date`. `date` приходит строкой `YYYY-MM-DD`.
* `model_version` — версия набора параметров. Пригодится в п. 1.3.

### 1.2. `GET /forecast/profiles` — список профилей

```json
[
  {
    "name": "default",
    "description": "Профиль по умолчанию ...",
    "model_version": "acys-v1",
    "params": {},
    "effective": { "history_start": "2022-07-01", "level_window": 15, "...": "..." },
    "error": null,
    "is_default": true,
    "enabled": true,
    "updated_at": "2026-09-13T11:02:53+00:00",
    "updated_by": "api-key-prefix"
  }
]
```

**Ключевое различие, на котором легко ошибиться:**

| поле | что это |
|---|---|
| `params` | **только переопределения.** Отсутствующий ключ = «используется значение по умолчанию». Пустой `{}` = не изменено ничего |
| `effective` | полный набор значений, с которыми реально пойдёт прогон: переопределения, наложенные на дефолты |

То есть `params` — то, что пользователь задал, `effective` — то, что получится. Оба нужны в интерфейсе, см.
п. 3.1.

`error` — не `null`, если сохранённый профиль перестал разрешаться (например, был записан под другую
`model_version`). Такой профиль **всё равно приходит в списке** — именно так его и можно починить. В этом
случае `effective` будет `null`: не падать, а показать строку с пометкой об ошибке и дать её отредактировать.

### 1.3. Запись

| метод | адрес | что делает |
|---|---|---|
| `POST` | `/forecast/profiles` | создать. Тело: `name`, `description`, `params`, `is_default`, `enabled` |
| `PATCH` | `/forecast/profiles/{name}` | изменить. Меняется только то, что прислали |
| `POST` | `/forecast/profiles/{name}/default` | сделать профилем по умолчанию |
| `DELETE` | `/forecast/profiles/{name}` | удалить |

Правила, которые сервер проверяет сам — их нужно отразить в интерфейсе, а не дублировать логикой:

* **`params` в `PATCH` ЗАМЕНЯЕТ набор переопределений целиком, а не сливается с ним.** Иначе переопределение
  нельзя было бы снять: отсутствие ключа уже означает «взять дефолт». Практически это значит: при сохранении
  отправлять полный текущий набор переопределений формы, а не дельту.
* **Значение `null` внутри `params` = «использовать значение по умолчанию»** и эквивалентно отсутствию ключа.
  Удобно, если проще отправить все ключи.
* Неизвестный ключ или значение вне границ — **422** с текстом, называющим поле. Ошибка приходит на
  сохранении, а не через час на сломанном прогнозе.
* Одноимённый профиль — **409**.
* Профиль по умолчанию **нельзя удалить** (422) и **нельзя выключить и оставить дефолтным**: сначала назначьте
  дефолтным другой. Дефолтный ровно один — это гарантия базы, а не проверка на фронте.
* `POST /forecast/profiles/{name}/default` снимает флаг с прежнего дефолтного в той же транзакции. Отдельный
  запрос на снятие делать не нужно.

### 1.4. Перекрёстное ограничение

Есть правило, которое **нельзя проверить по `min`/`max` одного поля**:

```
level_l <= level_window
```

(запасное окно не может быть шире основного). Сервер вернёт 422 с внятным текстом. На фронте желательно
подсветить это до отправки, но серверную проверку это не отменяет.

### 1.5. Как профиль связан с выгрузкой

* `POST /forecast/` принимает необязательное поле `profile` — имя профиля. Не передали — берётся дефолтный.
  Передали несуществующий — прогон падает, а не откатывается на дефолт молча.
* Карточка выгрузки в истории (`GET /forecast/snapshots`) показывает поле `profile` — **имя профиля, с которым
  реально считался прогон**. Для прогона без профиля там будет строка вида `defaults (no default profile)`.
* Повторная выгрузка того же запроса в тот же день не пересчитывается, а переливается из сохранённого
  прогона — **но только если параметры не изменились**. Сравниваются значения, а не имя профиля, поэтому
  правка `params` у дефолтного профиля корректно приводит к честному пересчёту.

## 2. Параметры

Для каждого: идентификатор, тип, границы, значение по умолчанию, **техническое описание** (то же, что отдаёт
`description` в схеме — можно показывать как подсказку) и **простое описание** (для обычного пользователя;
готовый текст, можно брать в интерфейс как есть).

### История

#### `history_start` — «Начало истории»

* Тип `date`, по умолчанию `2022-07-01`, границ нет.
* **Технически.** Жёсткая отсечка: факты раньше этой даты не участвуют в прогнозе вообще. Существует, чтобы
  пост-ковидный разгон 2021–2022 не втягивался в модель.
* **Простыми словами.** Дата, раньше которой полёты в расчёт не идут совсем. 2021 и начало 2022 — это ещё
  восстановление после ковида: самолёты летали заметно меньше обычного, и если впустить те месяцы, модель
  примет их за норму.
* **Сдвинуть раньше:** в расчёт вернётся ковидный провал — прогноз занизится, в сезонности появится «яма»,
  которой в обычный год не бывает.
* **Сдвинуть позже:** истории станет меньше, чем нужно модели; она перейдёт на аварийный расчёт (`level_l`), а
  сезонность почти исчезнет — по одному-двум наблюдениям на календарный месяц её не видно.

### Уровень (объём налёта)

Общий контекст группы, который стоит показать пользователю: **данные о полётах приходят с задержкой около пяти
месяцев**, поэтому свежие месяцы всегда выглядят пустее, чем были. Все три настройки ниже существуют ровно для
того, чтобы модель не приняла эту недогрузку за спад.

#### `level_window` — «Окно расчёта уровня, месяцев»

* Тип `int`, по умолчанию `15`, границы `3 … 36`.
* **Технически.** Сколько последних месяцев рассматривается при оценке уровня. Внутри окна остаются только
  ПОЛНЫЕ месяцы (см. `level_complete_frac`). Окно должно быть заметно длиннее лага загрузки FR24 (~5 месяцев),
  иначе в нём нет ни одного полного месяца, эталон полноты берётся из недогруженных, фильтр слепнет и уровень
  занижается. Бэктест с симуляцией лага (wMAPE): `3→22.6%`, `6→20.9%`, `9→12.9%`, `12→12.9%`, `15→12.6%`,
  `18→12.6%`, `24→13.5%`. Обрыв между 6 и 9, плато 9–18, 24 начинает втягивать устаревший режим. 15 — центр
  плато.
* **Простыми словами.** Окно, из которого модель берёт «типичный месяц». Внутри окна она сама отбирает месяцы,
  похожие на полные, и считает по ним.
* **Уменьшить (к 3):** худший из возможных выборов. Окно целиком попадает в зону недогруженных данных,
  сравнивать не с чем, отбор перестаёт работать — прогноз занижается, ошибка почти вдвое выше (22,6% против
  12,6%).
* **Увеличить (к 36):** в расчёт попадает то, как авиакомпания работала три года назад — другой флот, другие
  маршруты. Ухудшение мягче (13,5%), но прогноз отстаёт от сегодняшней реальности.

#### `level_complete_frac` — «Порог полноты месяца»

* Тип `float`, по умолчанию `0.85`, границы `0.1 … 1.0`.
* **Технически.** Месяц окна считается ПОЛНЫМ, если его дезонализованный объём ≥ этой доли от эталона
  (0.75-квантиль внутри окна). Ниже — месяц признаётся недогруженным по FR24 и исключается из расчёта уровня.
* **Простыми словами.** Планка, по которой месяц признаётся «данные пришли целиком»: модель смотрит на лучшие
  месяцы окна и оставляет те, что набрали не меньше 85% от них.
* **Опустить (к 0.1):** пройдут все месяцы, включая недогруженные — прогноз занизится. Фильтр перестанет
  делать то, ради чего он есть.
* **Поднять (к 1.0):** останутся только самые удачные месяцы — прогноз завысится и будет опираться на два-три
  месяца, так что один хороший месяц начнёт двигать весь результат.

#### `level_l` — «Запасное окно, месяцев»

* Тип `int`, по умолчанию `3`, границы `1 … 12`. Дополнительно: `level_l <= level_window`.
* **Технически.** Аварийный путь: используется ТОЛЬКО когда истории меньше 3 месяцев или ни один месяц окна не
  прошёл порог полноты. Тогда уровень = медиана последних N месяцев как есть, без фильтрации.
* **Простыми словами.** Запасной расчёт на случай, когда обычный невозможен. В нормальной работе не участвует
  вообще.
* **Уменьшить (к 1):** уровень повиснет на одном последнем месяце — скорее всего недогруженном, без всякого
  усреднения.
* **Увеличить (к 12):** устойчивее, но смешает лето с зимой и утянется вниз недогруженным хвостом.
* **Отдельно стоит показать в интерфейсе:** если этот параметр на что-то влияет — это симптом, что мало
  истории или слишком высок `level_complete_frac`.

### Сезонность

#### `seas_k` — «Сглаживание сезонности»

* Тип `float`, по умолчанию `3.0`, границы `0.0 … 24.0`.
* **Технически.** Сжимает сезонный коэффициент к 1.0 тем сильнее, чем меньше месяцев его подтверждают:
  `вес = n / (n + K)`. Больше K — площе прогноз. Меньше — заметнее сезонность, но тонкий растущий подпарк
  начинает принимать свой ранний разгон за сезонный провал. 3 — проверенная нижняя граница, ниже артефакт
  появляется.
* **Простыми словами.** Чем меньше данных по конкретному месяцу, тем сильнее модель «притягивает» его к
  среднему. Это число задаёт силу притяжения.
* **Уменьшить (к 0):** осторожности нет вовсе. У молодого растущего подпарка первые месяцы (мало бортов — мало
  рейсов) модель примет за сезонный спад и начнёт повторять его каждый год.
* **Увеличить (к 24):** сезонность схлопнется полностью, прогноз станет ровной линией через год.

### Граница данных

#### `frontier_frac` — «Порог покрытия месяца»

* Тип `float`, по умолчанию `0.6`, границы `0.1 … 1.0`.
* **Технически.** Месяц считается покрытым, если его объём ≥ этой доли от медианы окна `frontier_window`.
  Последний покрытый месяц — фронтир: история подгоняется до него, прогноз стартует с фронтир+1.
* **Простыми словами.** Где в отчёте заканчивается факт и начинается прогноз.
* **Опустить (к 0.1):** покрытым признаётся почти любой месяц, включая полупустой. Граница уедет вперёд, и
  недогруженные месяцы останутся в отчёте КАК ФАКТ — на стыке будет видна яма.
* **Поднять (к 1.0):** граница отъедет назад, свежие настоящие данные окажутся перекрыты прогнозом — отчёт
  потеряет факт там, где он есть.

#### `frontier_window` — «Окно границы, месяцев»

* Тип `int`, по умолчанию `9`, границы `3 … 36`.
* **Технически.** Сколько последних месяцев идёт в медиану, относительно которой измеряется `frontier_frac`.
* **Простыми словами.** С чем сравнивать месяц, решая, закрыт он или нет.
* **Уменьшить (к 3):** медиана посчитается по самому недогруженному хвосту, планка упадёт — та же яма на
  стыке, что и при низком `frontier_frac`.
* **Увеличить (к 36):** точкой отсчёта станут старые месяцы другого масштаба флота, планка поднимется, граница
  отъедет назад.

### Структура маршрутов

#### `min_route_pool` — «Минимальный пул маршрутов»

* Тип `int`, по умолчанию `5`, границы `1 … 100`.
* **Технически.** Если в шаблонном месяце суб-флота меньше этого числа различных маршрутов, пул считается
  вырожденным и расширяется каскадом: суб-серия за всю историю → мастер-серия за всю историю. Защита от
  «один самолёт весь месяц летал одним маршрутом».
* **Простыми словами.** Сколько разных маршрутов должно найтись у типа самолёта, чтобы набор считался
  пригодным. Не хватило — модель расширяет поиск.
* **Уменьшить (к 1):** защита отключается. Это уже случалось в проде: борт, отлетавший месяц по одному
  маршруту, дал в прогнозе 36 повторов этого маршрута на 226 часов подряд.
* **Увеличить (к 100):** почти все типы провалятся к расширенному поиску, маршруты станут обобщёнными —
  прогноз по конкретной модели нарисуется маршрутами всего семейства.

### Горизонт

#### `horizon_years` — «Горизонт прогноза, лет»

* Тип `int`, по умолчанию `2`, границы `1 … 10`.
* **Технически.** Прогноз идёт от фронтира до «дата запроса + N лет». Последний месяц пропорционально урезается
  по дню запроса — тот же день задаёт конец контрактного года.
* **Простыми словами.** На сколько лет вперёд считать.
* **Уменьшить (к 1):** быстрее и легче, но если отчёт смотрит на два контрактных года вперёд — второй окажется
  пустым.
* **Увеличить (к 10):** десять лет будут посчитаны по примерно годовой истории — доверие к дальним годам
  иллюзорное. Цена тоже растёт: сейчас выгрузка на 2 года это ~1,2 млн строк, на 10 лет — примерно впятеро
  больше строк, времени и места.

#### `pax_load_factor` — «Коэффициент загрузки»

* Тип `float`, по умолчанию `0.8`, границы `0.1 … 1.0`.
* **Технически.** `Total PAX = Total Seats × коэффициент`. Применяется и к фактам, и к прогнозу.
* **Простыми словами.** Сколько кресел считается занятыми. Обычное умножение, ни на что другое не влияет — но
  меняет колонку пассажиров целиком, включая прошлые рейсы.
* **Опустить (к 0.1):** загрузка 10%, пассажиров в восемь раз меньше, чем при нынешних 80%.
* **Поднять (к 1.0):** полный самолёт на каждом рейсе; для регулярных перевозок заведомо завышено.

## 3. Требования к UI

### 3.1. Главное: показывать разницу между «не задано» и «задано ровно как дефолт»

Это центральная механика экрана. `params` хранит только переопределения, поэтому у каждого поля есть **три**
состояния, а не два:

1. **не переопределено** — ключа в `params` нет, значение берётся из схемы (`default`);
2. **переопределено другим значением** — ключ есть, значение отличается от дефолта;
3. **переопределено тем же значением, что дефолт** — ключ есть, значение совпадает с `default`.

Третье состояние имеет смысл сохранять как есть: пользователь мог осознанно зафиксировать значение. Но
интерфейс обязан показывать, что поле переопределено (например, маркер «изменено» и кнопка «вернуть к
умолчанию», которая **удаляет ключ**, а не вписывает дефолтное значение).

Рядом с полем полезно всегда показывать дефолт из схемы: «по умолчанию 15».

### 3.2. Что рисовать для каждого типа

* `int` с `min`/`max` — числовое поле + слайдер. Шаг 1. Числовое поле обязательно: у `min_route_pool` диапазон
  1…100, слайдером точное значение не поймать.
* `float` — числовое поле + слайдер с шагом 0.05 (у всех float-параметров диапазон 0.1…1.0, кроме `seas_k` с
  0…24 — там шаг 0.5).
* `date` — datepicker, без границ.
* `description` из схемы — подсказка (тултип или раскрывающийся блок). Тексты длинные, в подпись под полем не
  влезут.

Полезная деталь: **позиция дефолта на шкале сама по себе информативна**. У `min_route_pool` дефолт 5 при
диапазоне до 100, у `level_complete_frac` — 0.85 при 0.1…1.0. Метка дефолта на слайдере сразу показывает, что
«середина диапазона» и «нормальное значение» — разные вещи.

### 3.3. Сохранение

* Отправлять **полный набор переопределений**, а не дельту (см. п. 1.3: `params` замещается целиком).
* Валидацию `min`/`max` дублировать на клиенте для мгновенной реакции, но **ответ 422 всё равно обрабатывать**:
  правило `level_l <= level_window` перекрёстное, и его может не быть в клиентской логике.
* Текст ошибки из `details.msg` показывать как есть — он называет конкретное поле.

### 3.4. Список профилей

* Дефолтный профиль пометить явно: именно он используется, когда выгрузка не называет профиль.
* Не давать удалить дефолтный и не давать выключить его, оставаясь дефолтным — сервер это отклонит, но лучше
  не доводить до ошибки.
* Профиль с `error != null` показывать в списке с пометкой, форму открывать в режиме исправления. Не прятать:
  спрятанный сломанный профиль починить невозможно.
* `updated_at` / `updated_by` — полезны в списке: видно, кто и когда трогал параметры модели.

### 3.5. Что сказать пользователю на самом экране

Короткий блок помощи, который снимает большинство вопросов:

* заводские значения подобраны по историческим проверкам, а не наугад;
* менять имеет смысл по одному числу за раз — иначе непонятно, что дало эффект;
* для экспериментов заводить **отдельный профиль**, дефолтный тогда остаётся точкой возврата;
* после изменения параметров повторная выгрузка честно пересчитается, старый отчёт не подсунется;
* два самых опасных значения — `level_window` около 3 и `min_route_pool` = 1. Обе ошибки тихие: прогноз
  посчитается и будет выглядеть правдоподобным.
